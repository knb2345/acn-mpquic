Frame-aware multipath QUIC
with a learned bandwidth predictor

Streaming live lectures over two mobile connections without the video freezing

On real cellular networks, standard schedulers deliver 16.4%–18.2% of video frames too late. Ours: 10.6%–13.5%.

Kabir Bajaj and Team 7 · 29 October 2026

Slide 1. A phone with two SIM cards has two internet connections. We send a live lecture over both at once, and we built a scheduler, helped by a small neural network, that decides which connection each video frame takes so it arrives in time. The box is the headline result.

The setting

  • Students watch live lectures on a phone with mobile data
  • Many phones have two SIM cards: two connections, each slow and unsteady (a few Mbit/s, 50–150 ms delay)
  • Multipath QUIC uses both at once; a scheduler picks the path for every packet
I-frame: full picture, ~55 KB, every 2 sP-frame: only the changes, ~8 KB, 24 per second

Frame i, produced at time si, must arrive completely by si + D, with playback delay D = 300 ms. If not, it is a deadline miss and the video freezes.

Slide 2. QUIC is the modern transport protocol behind YouTube and Google; multipath QUIC lets one connection use two networks. The scheduler is the part that decides which network each packet goes on. Video is a sequence of frames: a big full picture (I-frame) every 2 seconds and small difference frames (P-frames) in between. The player shows each frame D = 300 ms after it was made; a frame that is late or incomplete causes a freeze. The big I-frames are the risky ones.

The problem: schedulers see bytes, not frames

  • MinRTT (TQUIC's default): next packet on the lowest-delay path with room
  • Round-robin: alternate between paths
  • ECF (earliest completion first): wait for the fast path if that finishes sooner
  • Redundant: every packet on both paths (half the capacity spent on copies)
  • None knows where a frame starts or ends, or when it is due: a split frame waits for its slower half, and small frames get stuck behind big ones
Example: one I-frame on a slow path
45 KB × 81.5 Mbit/s + 30 ms = 270 ms

That is 270 of the 300 ms budget, before counting frames already queued.

Research questions: (1) how often do standard schedulers miss deadlines? (2) can a scheduler that knows each frame's size and deadline, with a learned speed prediction, do better? (3) which part of the design matters?

Slide 3. MinRTT sends on the lowest-delay path that has room; round-robin alternates; ECF waits for the fast path if that would finish sooner; redundant sends everything twice. None of them knows about frames. The example: 45 kilobytes is 360 kilobits; at 1.5 megabits per second that is 240 ms of sending, plus 30 ms of travel. On slow links there is no room for a bad choice. Question 3 is answered with ablations: versions of our scheduler with one part removed.

Our scheduler: predict when each frame will arrive

Tp = Qp + SBp + dp

Tp arrival time on path p · S frame size · Qp bytes waiting ahead of it · Bp path speed · dp = sRTTp/2 one-way delay

Rule 1: whole frame if a path makes it
p* = argminp Tp
use p* if  Tp* ≤ h · (deadline − now)

Then all S bytes go on p*. Safety margin h = 0.85 for the hand-tuned version, h = 1 for the learned one (its prediction is already cautious).

Rule 2: otherwise split, both parts finish together
T* = S + QA + QB + BAdA + BBdBBA + BB
sp = Bp(T* − dp) − Qp

sA + sB = S, and both parts arrive at the same time T*.

Qp = bytes of earlier frames planned for p + max(0, in-flightp − Bp·minRTTp). Each path sends only its own frames, so small frames overtake big ones. A frame already past its deadline may use any path.

Slide 4. The formula: to know when a frame arrives on a path, add up everything waiting ahead of it plus the frame itself, divide by the path's speed, and add the one-way delay. Rule 1: pick the path with the earliest arrival; if it makes the deadline, the whole frame goes there. The hand-tuned version keeps a 15% safety margin. Rule 2, mostly for big I-frames: split the frame so both parts land at the same time. Setting the two arrival times equal and the two parts summing to S gives T-star and each part's size. Q_p also counts data stuck in the network's queue: bytes in flight beyond what the path holds at its minimum RTT. Everything depends on B_p, the speed, which is what the neural network predicts.

The ML part: predicting the speed Bp

  • If Bp is too high, rule 1 trusts a path that will be late. BBR's own estimate is too high 38.2% of the time on our test recordings.
  • Input x: 44 numbers per path from the last second (delivery rate, send rate, queueing delay, loss, cwnd, BBR's estimate, ...)
  • Target: y = ln(1 + C/1000), C = true average speed over the next 0.5 s (bytes/s)
  • Data: 6 recorded cellular networks for training, 2 others for testing
What the scheduler uses
Bp = 1000 (eŷ0.1 − 1)  ⇒  P(C < Bp) ≈ 10%
Small neural network (MLP): 44 → 32 → 32 → 4
h1 = ReLU(W1x + b1)
h2 = ReLU(W2h1 + b2)
ŷ = W3h2 + b3

Four outputs ŷτ: the 10th, 20th, 30th and 50th percentile (τ = 0.1, 0.2, 0.3, 0.5).

Pinball loss
Lτ(y, ŷ) = max(τ(y − ŷ), (τ − 1)(y − ŷ))

For τ = 0.1, too high costs 0.9, too low 0.1: 9× penalty for overestimates.

Slide 5. Motivation first: the formula is only as good as the speed estimate, and a high estimate is the dangerous error. The model reads the last second of each path and predicts the speed for the next half second, in a log scale so that slow and fast links are treated alike. It is a two-layer network; ReLU just sets negative values to zero. It outputs four percentiles instead of one guess. The pinball loss is the standard loss for percentiles: for the 10th percentile, an overestimate is penalised nine times more than an underestimate, so the model learns a value the real speed stays above 90% of the time. That cautious value is B_p. The weights are compiled into TQUIC's Rust code, and Rust and Python agree to 0.002%.

Result 2: fewer late frames on real cellular networks

Trace scenario, median of 5 runs. Blue = ours. Shorter is better. Redundant 52.8% and single path 72.9% are off the scale.

  • Late frames: 10.6%–13.5% with ours vs 16.4%–18.2% standard
  • Run by run, learned beats MinRTT and ECF in 3 and 3 of 5 runs; freezes less in 4 and 4 of 5 (1.3 s vs 1.6–1.8 s per minute)

Slide 8. The chart shows, for each scheduler, the share of the lecture's frames that arrived after their deadline on the real recordings. Both of our versions beat every standard scheduler, and the order is the same with 150 ms and 500 ms deadlines. Freezing time models a player that waits for late frames: it shows frame i at max(previous + frame interval, completion time), and every extra wait counts. The frame-pin ablation shows the deadline check and the split are what help, not just keeping frames whole. On fast links every scheduler is fine; on the slow constant links (3.3%–4.9% missed) the big I-frames barely fit a 300 ms budget for anyone.

Conclusions

What we found
  • Planning frames against deadlines cuts late frames from 16.4%–18.2% to 10.6%–13.5%
  • Our ML model is the most accurate speed estimate
  • But it is too cautious: the hand-tuned version is still a bit better (10.6% vs 13.5%; learned better in 2 of 5 runs)
Limitations
  • Emulated network, not a live one
  • Recordings from US networks
  • One 60 s lecture, 5 runs each
Next steps
  • Choose τ from the predicted spread: less caution on steady links
  • Retrain on the learned scheduler's own traffic
  • More recordings, longer lectures
